# 企业级智能客服 Agent 架构验证

> 研究日期：2026-09-03（第三轮：补 2026 年新材料 + 小红书渠道定性）
>
> 前两轮：2026-09-02 建立框架并补入一手生产案例。
>
> 范围：验证基于 B 站案例归纳的企业级智能客服 Agent 架构，并用官方一手文档与已落地案例的工程博客核对关键能力。第三轮重点是时效性——前两轮证据以 2025 年材料为主，本轮补入 2026 年（尤其 6-9 月）的生产复盘与协议变更。

## 结论摘要

主干成立，但需要补强五个边界（前三条为第一轮结论，后两条由第二轮一手案例带出）：

1. **Agent 编排必须持久化状态、支持恢复和人工介入**，不能只有一次性 LLM 调用。
2. **RAG 只负责知识 grounding**；订单、物流、库存、CRM、工单等实时业务必须通过受控工具/API 访问。
3. **生产闭环必须包含权限、审计、失败重试、人工转接、观测和评测**。这些不是外围能力，而是客服系统的一部分。
4. **确定性约束的适用范围比预想的大**：不只是退款改址这类高风险流程，连「要不要调工具」「派给哪个 Agent」都不应交给主 LLM 自由裁量。
5. **评测指标的结构性错误比指标缺失更危险**：必须区分 deflection（路由指标）与 resolution（质量指标），并预设人工基线和满意度下限门槛。

## 证据分层

### 一档：已落地的生产案例（一手工程博客）

#### Swiggy × Databricks（2025-10）

[Redefining Customer Support: Swiggy's Enterprise-Scale AI Agent Built with Databricks](https://www.databricks.com/blog/redefining-customer-support-swiggys-enterprise-scale-ai-agent-built-databricks)

目前公开材料中架构披露最完整的一例，价值在于它写出了**演进路径中每一步的死因**：

| 阶段 | 形态 | 被放弃的原因 |
|------|------|-------------|
| 1 | LLM 意图分类 + LLM 回复格式化（两层管线） | 上下文处理与扩展性撑不住 |
| 2 | 加 RAG | 每个意图需手写分支（硬编码）；**RAG 无状态，多轮会话丢上下文**；无反馈回路 |
| 3 | 转 Agentic（图式节点执行） | —— 获得有状态会话、模块化分支、反馈回路、逻辑与意图解耦 |
| 4 | 转多智能体 | 单 Agent 处理多意图会话时功能无法隔离、维护成本高、输出质量下降；改为按 disposition 各起一个 Agent 实例 |

写入架构设计原则的条目：AI Gateway 集中管理权限/限流/payload 日志/流量兜底；Gateway Guardrails 在模型端点拦截不安全与不合规内容；MLflow 3.0 做全链路 tracing 与在线抽样评测；Unity Catalog 管理数据与 AI 资产；CRM 采用 **action-trigger 信号式集成**（Agent 产生决策 → 发出 action signal → CRM 后端执行）；**组件级 fallback，含 LLM 自动降级**；向人工坐席优雅降级；整体状态管理用于改善结果和故障恢复。

生产踩坑（对本项目最有参考价值的部分）：

- **过度依赖短期记忆**：Agent 误判「记忆里已有数据」而不调工具，导致回复过期信息。修法是信号区分静态/动态 + prompt 强制刷新 + **在工具调用上加确定性约束（强制至少调用一个工具，而不是让工具调用可选）**。
- **Agent 分派全交给 LLM 只有 90% 准确率**：改为规则路由（意图触发）+ 拆出专用轻量 LLM 承担分派，把分派任务从主 Agent 解耦。
- **多模型按任务复杂度分级**：简单模型 / 小推理模型 / 大推理模型三档并存，控成本与延迟。
- **微调遭遇灾难性遗忘**，投入产出不划算，回退到 prompt 工程。
- 成本优化细到 prompt 去除 emoji 省 token、few-shot 降为 single-shot。

指标可信度提示：该文同时声称「100% 查询全自动、无人工介入」与「需要向人工优雅降级」，两者矛盾；「p99 < 500ms」对完整 LLM 回复不现实，更像组件级 KPI。这是厂商联署博客，业务指标按宣传口径处理，**架构与踩坑部分可信度高于指标部分**。

#### Diffco：中型 SaaS 客服 Agent 拆解（2026-06）

[Multi-agent system architecture: a teardown of how we built a customer support agent](https://diffco.us/blog/multi-agent-system-architecture-how-we-built-a-customer-support-agent/)

2026 年最完整的第三方生产复盘。客户为 4000 家客户、5 人客服团队的 B2B SaaS，工单量年增 40% 而人力未增；系统当前在产处理每周五位数工单。作者明确声明数字经过脱敏调整，但设计决策与权衡为真实。

**独立复现了 Swiggy 的演进路径**（两者互不相关，结论一致，可信度显著提升）：

| 迭代 | 形态 | 失败原因 |
|------|------|---------|
| 1 | 单 LLM + 全量工具 | 系统提示词膨胀到 4000 token；**类别间指令相互串扰**——能正确识别类别却错误执行；且用旗舰模型价格做本该廉价的分类 |
| 2 | 小模型路由 + 单一 solver | 串扰消失，但单一提示词无法同时照顾简单类别和复杂类别 |
| 3 | 路由 + N 个专家 solver | 评测集解决率 58% → 81%。但**约 7% 工单跨两个类别**，路由二选一导致答案缺失一半 |
| 4（已上线） | 路由 + 编排器 + 专家 + 终审 | 评测集 87%，生产首月 84%，三个月后 88% |

作者的原话值得直接引用：「我们不是从『要建多智能体』出发的。我们从一个问题和一个评测集出发，架构在四次迭代中变成多智能体，是因为单 Agent 一直撞墙。这个选择是挣来的。如果你只因为多智能体有意思就直接跳过去，你会超支。」

**上线架构的六个阶段**（比 Swiggy 披露得更细）：

1. **接入与归一化**：解析发件人身份、附件、语言、历史；解析到客户记录并加载紧凑账户上下文（套餐等级、历史工单摘要、当前账单状态、近期用量）。**纯代码，零模型调用**，产出结构化对象供后续所有阶段使用。
2. **分诊分类器**：Haiku 级小模型一次调用，多标签判定类别 + 紧急度 + 是否可能需要人工，严格 JSON schema 输出。成本不到一分钱、500ms 内完成，**门控下游全部流程**。紧急或判定需人工的，直接带结构化上下文进人工队列。
3. **专家 Agent 并行**：每个被标记的类别跑一个专家。各自持有约 800 token 的聚焦提示词（而非 4000）、**仅限本域的工具子集**（账单专家能读发票、提议套餐变更，但不能改集成配置）、独立评测集、独立提示词版本轨。专家有三种返回：带引用的完整答案 / 部分答案+请求编排器协助 / 升级人工。
4. **编排器**：多个专家有输出时才介入，**只做拼接和冲突消解，不重做工作**。关键设计：**编排器没有任何工具**，不能执行动作，以此保持故障模式简单。
5. **终审（Reviewer）**：二次模型对照检查表校验草稿——是否正确引用真实账户数据、是否提议了需用户明确确认的动作、是否越出策略边界、语气是否符合品牌。**终审不通过则连同草稿一起进人工队列供编辑**。
6. **动作确认**：任何改变状态的动作（套餐变更、退款、集成凭证重置）**永远不由 Agent 执行**。回复中带确认链接/按钮，用户明确确认后，才由确定性后端服务执行。作者称这是「整个系统中最重要的一条设计规则」。

**明确拒绝的流行做法**（每条都是刻意选择）：

- **不做 Agent 间自然语言对话**：「Agent 用自然语言互相辩论」在演示里好玩，在生产中不稳定。专家之间不通信，编排器读结构化输出做拼接——**Agent 间通信是 JSON，不是英语**。
- **严格工具边界**：每个 Agent 只有最小必需工具集，行为异常的爆炸半径被其工具清单限死。
- **无自主动作**：面向客户的系统里这是不可谈判的。Agent 建议，不执行任何触及金钱、身份或外部系统的操作，用部分自动化面积换取极大简化的安全论证。

**真实数字**：解决率生产首月 84%、三个月 88%；端到端中位延迟 9 秒、p95 18 秒（专家并行；串行会是 25 秒以上，作者指出**若是实时聊天场景就要重新考虑架构**）；升级人工的 13-16% 带完整 transcript、结构化账户上下文和已写好的草稿回复进队列，**人工是在编辑而不是从零开始，作者称大部分时间节省实际来自这里——即使没能自动化的工单也快了 4 倍**；Agent 解决工单的 CSAT 与人工解决在统计噪声内持平。

**作者自陈的两个遗憾**之一：在专家还不稳定时就建了编排器，专家一旦回归劣化，编排器会继承这个劣化。



[How We Built a World-Class Reranker for Fin](https://fin.ai/research/how-we-built-a-world-class-reranker-for-fin/)

检索链路披露到实现级：**会话摘要成短查询 → 向量召回 top-K=40 → 自研 reranker 重排 → context budget filter 截断至约 1500 token → 生成**。

- 自研 reranker 基于 ModernBERT-large，RankNet pairwise loss，40 万条真实查询 × 40 候选（1600 万 pair）训练，标签来自 LLM pointwise reranker。
- 对比 Cohere Rerank-v3.5：MAP +17.5%、NDCG@10 +16.7%、Recall@10 +13.1%；reranker 成本降 80%；P50 延迟约 150ms 不变。
- 三级评测漏斗：3000 条静态集离线指标 → 1500 条真实会话过冻结管线测引用精召 → 150 万会话线上 A/B。
- **租户隔离在检索层硬做**：passage 独立编码互不影响，查询时只从同一 workspace 检索，查询向量用完即弃，避免 PII 泄漏。
- **主指标只有一个：resolution rate（无人工介入即解决的会话占比）**；副指标 answer sent rate（直接作答而非追问澄清的比例）。

#### Klarna（反面案例）

[Klarna AI reversal postmortem](https://internative.net/insights/blog/klarna-ai-reversal-postmortem)

2024 年宣称 AI 承担 700 名客服的工作量、处理 2/3~3/4 会话；2025 年 5 月反转，重新招聘人工。CEO 公开承认成本在评估中权重过高，导致质量下降。

复盘的核心论点，直接决定本架构的评测设计：

- **「AI 处理了 X% 的会话」是路由指标，不是质量指标。** "handled" 不等于 "resolved"，不等于客户满意，不等于没有二次来访。
- **deflection rate 与 resolution rate 被混为一谈**：deflection（AI 作为首个响应者接走的比例）上 AI 一定好看，resolution 往往不。两者之间的差值就是客户关系静默流失的地方。
- **满意度是滞后指标**：6~12 个月才显形，与流失率对上已是 18 个月后。
- 可执行动作：第一周就埋 resolution rate；**必须建立 AI 上线前的人工基线**，没有基线就不得把成本节省归因于 AI；上线前预先写死满意度下限门槛，破线即停止对外宣称收益。

### 二档：厂商参考架构（官方文档）

- [Salesforce Agentforce 参考架构](https://developer.salesforce.com/docs/einstein/genai/guide/agentforce-reference-architectures.html)：标准分层为 **Topics/instructions（范围与人设）+ Actions（工具）+ Guardrails**。Guardrails 定位关键——它**同时拦截输入 prompt、校验 Agent 提议的动作、过滤最终回复**，是三点拦截而非只在输出侧。链路：渠道 → 判定 topic 范围并施加 guardrails → prompt 模板组装（Flow/Apex 触发后端逻辑）→ 经 RAG retriever 从 Data 360 + 向量库 + CRM 取上下文 → 作答 → 无法解决则升级人工，**并把完整会话记录一并转交**，由 Omni-Channel 分派、Omni Supervisor 管理优先级与坐席容量。
- **MCP 2026-07-28 规范修订（协议核心转为无状态）**：[AWS Architecture Blog（2026-09-01）](https://aws.amazon.com/blogs/architecture/mcp-went-stateless-is-your-aws-mcp-server-deployment-well-architected/)。这是本轮时效性检查中最重要的变更，直接影响工具层设计：
  - `initialize` 握手与 `Mcp-Session-Id` 头取消，每个请求自带协议版本与客户端上下文，任意服务实例都能响应。**粘性会话、共享 session store 不再必要**；新增 `server/discover` 用于能力发现。
  - **无状态描述的是协议，不是应用**。需要跨调用连续性时，工具返回一个状态标识符，模型在后续调用中携带；状态留在你的数据存储里，模型只带 key。相比旧模型的优势是标识符位于模型上下文中而非隐藏在 header 里，模型可以对它推理并在工具间传递。
  - **服务端不能再在调用中途向客户端推送请求**——确认（elicitation）、sampling、root 查询原先依赖保持打开的流。新机制是 **MRTR（Multi Round-Trip Requests）**：服务端返回 `input_required` 结果，内含 `inputRequests` 映射和不透明的 `requestState` 令牌；客户端完成后携带 `inputResponses` 与回显的 `requestState` 重发原调用。**这正是"动作确认"模式在协议层的标准实现**。
  - **幂等性从工程建议升级为协议级要求**：旧的流恢复（`Last-Event-ID`）被取消，规范明确要求"让工具幂等，客户端重发中断的调用"。
  - 可观测性改为 `_meta` 中的 W3C Trace Context 做分布式追踪、`stderr` 或 OpenTelemetry 做日志，**协议内置日志通道已废弃**。
  - 迁移警告：规范含向后兼容通道，服务 2025 年客户端期间不得删除粘性会话与 session store；应按请求记录协议版本、设定日落期、流量归零后再下线。

- [LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)：图式编排、持久化 checkpoint、恢复执行、人工介入。验证会话状态、可恢复流程和 HITL 属于编排层。
- [Dify Agent](https://docs.dify.ai/en/use-dify/build/agent) / [Knowledge](https://docs.dify.ai/en/use-dify/knowledge) / [Tools](https://docs.dify.ai/en/use-dify/tools)：将 Agent、知识检索、外部工具分开建模，验证「RAG + 工具调用」而非「RAG 包打天下」。
- [Microsoft Copilot Studio 架构指导](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/architecture) 与 [人工转接](https://learn.microsoft.com/en-us/microsoft-copilot-studio/advanced-hand-off)：权限、审计、监控、转人工不是可选装饰。
- [pgvector](https://github.com/pgvector/pgvector)：HNSW/IVFFlat 索引路线，`PostgreSQL + pgvector` 适合中小规模知识库的务实起点，不等于所有规模都固定用它。
- [OpenTelemetry](https://opentelemetry.io/docs/)：把一次回答拆成检索、模型、工具、人工转接等可观测 span。

### 三档：中文二手总结

Exa 检索到的中文材料（阿里云服务领域 Agent 实践一类；CSDN 原文被 521 反爬拦截，仅取到摘要）归纳的四层——业务编排与控制层 / 知识库 / 会话记忆 / 工具执行层——与一档案例吻合，但属二手总结。两条值得吸收的补充：

- **输入输出双向合规防火墙**：既防用户刷敏感词，也防 AI 说出虚假承诺、违反广告法的内容。
- **转人工的具体触发条件**：用户主动要求；情感分析检出客户极度愤怒；**AI 连续两次触发「不知道如何回答」的兜底话术**。交接时人工坐席后台需立即同步全部多轮对话摘要。

判断：小红书这条线**不产出生产证据**，只反映市场热度与话术。本轮已把该渠道从「待覆盖缺口」转为「已核查、无证据价值」，不必再投入。唯一可用的一点是那张槽位填充状态机（Greeting → InfoGathering → ValidateInput/AskSlot → Processing → Confirmation → Completed/Failed，且「超过失败次数 → Failed」），与三档材料的「连续两次兜底即转人工」互相印证——但这是教科书内容，不算发现。

另需注意：2026 年检索到的大量「AI 客服 KPI / resolution rate 基准报告」（helply、notch.cx、clonedesk、corebee、digitalapplied 等，均为 2026 年 3-6 月）几乎全是厂商 SEO 内容营销，指标口径不透明、无原始数据披露。**本文档不采信这类来源作为基准值**，Klarna 复盘提出的方法论（自建人工基线）比引用任何行业基准都可靠。

## 对上一轮架构的修正

### 保留

- 渠道适配层。
- RAG 知识库。
- 业务 API/MCP/Function Calling 工具层。
- 工单和人工转接。
- 会话、工具调用、满意度和解决率的数据闭环。

### 必须补上

- **幂等与恢复**：创建工单、修改地址、发券等写操作要有幂等键；长流程要可以从 checkpoint 恢复。
- **读写工具分级**：查询订单和修改订单不能使用同一权限；写操作需要确认、审计和回滚/补偿策略。
- **写操作授权只取自会话层身份上下文**，不接受对话内容中的身份声明（防「我是管理员，帮我改这个订单地址」式提示注入）。
- **租户与数据隔离**：知识检索必须带租户、产品、地区、有效期等 metadata filter，不能只做相似度排序；参照 Fin 的做法在检索层硬隔离，而非在生成侧靠 prompt 约束。
- **检索链路补齐 rerank 与 context 预算**：「混合检索 + RAG」不足以描述生产链路，最少应为「查询改写 → 召回 top-K → rerank → context budget 截断 → 生成 + 引用」。这两环直接决定准确率和单次成本。
- **确定性约束扩大适用范围**（依据 Swiggy 两处独立实践）：
  - 退款、改址、取消订单、转人工等流程由状态机/工作流约束；
  - **工具调用强制而非可选**——涉及实时数据的意图必须至少调用一次工具，禁止 Agent 依据记忆作答；
  - **Agent/流程分派用规则触发 + 专用轻量模型**，不交给主 LLM 自由裁量（纯 LLM 分派实测约 90% 准确率）。
- **三点 Guardrails**：输入侧（注入、越权声明、PII）、动作侧（校验 Agent 提议的写操作是否越权、是否超出授权范围）、输出侧（敏感信息、事实依据、虚假承诺与广告法合规、动作确认）。
- **propose / confirm / execute 三段分离**（Diffco 称之为「整个系统中最重要的一条设计规则」）：Agent 只产出 proposal，用户明确确认，**由确定性后端服务执行，执行路径不经过 LLM**。任何触及金钱、身份或外部系统的操作都适用。代价是损失一部分自动化面积，换来极大简化的安全论证。在 MCP 上的标准实现方式是 MRTR（`input_required` + `requestState`）。
- **终审（Reviewer）节点**：生成之后、发出之前，由二次模型对照检查表校验——是否正确引用真实账户数据、是否提议了需确认的动作、是否越出策略边界、语气是否符合品牌。**不通过则连同草稿转人工供编辑**。Diffco 的经验是大部分时间节省实际来自这里：即使没能自动化的工单，人工也因为「在编辑而非从零开始」而快了 4 倍。
- **Agent 间通信用结构化数据，不用自然语言**：「多个 Agent 用自然语言互相辩论」在演示里好玩，在生产中不稳定。专家之间不直接通信，由无工具的编排器读结构化输出做拼接。
- **工具幂等**（MCP 2026-07-28 后为协议级要求）：流恢复机制取消，客户端会重发中断的调用。退款、建单等写操作必须带幂等键去重。

- **降级与兜底路径**：LLM 超时/限流/故障时的行为必须显式定义——LLM 自动切换 → 组件级 fallback → 固定话术 + 排队转人工。客服系统可以答得不够好，不能没有响应。
- **成本与上下文预算硬约束**：历史截断策略、检索 top-K 上限、**单会话最大工具调用轮次**（无轮次上限的 Agent 会自旋）、按任务复杂度分级选模型。
- **知识库生命周期**：谁审核、如何版本化、过期文档如何立即失效。客服答错的代价主要来自过期知识，而非检索算法。
- **PII 与合规留存**：审计日志会存全量对话，含手机号与地址，需脱敏规则与留存期限。
- **评测门禁（区分主次，不可并列摆放）**：
  - **主指标：resolution rate**（无人工介入且无二次来访的解决占比）。
  - 参考指标：deflection rate / 自动化率——**这是路由指标，不得单独用于论证收益**。
  - 其余：知识命中率、事实正确率、工具调用正确率、转人工率、P95 延迟、单会话成本、投诉率。
  - **门禁条件**：上线前必须建立人工基线；预先写死满意度下限门槛，破线即回滚并停止对外宣称收益。

## 最终判断

> **企业客服 Agent = 渠道接入 + 前置拦截 + 会话状态 + Agent/工作流编排（含确定性约束）+ 分级检索 grounding + 受控业务工具（幂等）+ 工单/人工协同 + 三点 Guardrails + 终审 + propose/confirm/execute + 降级兜底 + 治理审计 + 以 resolution rate 为主指标的评测闭环。**

「大模型 + 向量库」只能覆盖知识问答，不能独立构成已落地的企业客服 Agent。

关于多智能体：**不是起手就要的，但有明确的触发线**。两个独立案例给出了一致的结论——Swiggy 是在单 Agent 上线后暴露「多意图会话下功能无法隔离、维护成本高、质量下降」才拆的；Diffco 更直白：「我们不是从『要建多智能体』出发的。我们从一个问题和一个评测集出发，架构在四次迭代中变成多智能体，是因为单 Agent 一直撞墙。这个选择是挣来的。如果你只因为多智能体有意思就直接跳过去，你会超支。」

判断标准建议为：跨业务域的强类型工具超过 20~30 个，或单一提示词已无法稳定路由多意图会话（Diffco 实测约 7% 工单跨两个类别，路由二选一会丢失一半答案）。在此之前，一个编排器 + 多个强类型工具 + 确定性流程更容易控制风险和验收。

拆分时的两条经验：拆分维度应为**业务处置类型**（Swiggy 的 disposition、Diffco 的 ticket category）而非技术模块；且**先让专家稳定再建编排器**——Diffco 自陈的遗憾正是反过来做，导致专家一旦回归劣化，编排器会继承这个劣化。
