# 置信度阈值标定

本文说明「知识问答的置信度闸门」这套参数是怎么来的、什么时候会失效、失效了怎么发现。
对应实现：

| 关注点 | 落点 |
|--------|------|
| 判决逻辑 | `src/nodes/confidence.ts` |
| 参数与其前提（profile） | `src/confidence/profile.ts` |
| ROC / PR / 工作点 / 坐标下降（纯数学） | `src/confidence/calibration.ts` |
| 标定流水线（分组、分阶段、采集契约） | `src/confidence/calibration-runner.ts` |
| CLI | `scripts/calibrate-threshold.ts`（`pnpm calibrate`） |

---

## 1. 为什么阈值必须标定，而不是写一个常数

阈值只在**标定它的那个前提下**成立。三个常见变化都会让它静默失效：

| 变化 | 失效机理 | 现象 |
|------|----------|------|
| 换一版 rerank 模型 | 分数量纲整体平移（8B → 4B 可能让同一 chunk 从 0.6 掉到 0.4） | 兜底率骤升，或反过来几乎不兜底 |
| 知识库 100 篇 → 1 万篇 | 负样本变多也变"近"，整体分数分布下移 | 噪声成群挤进 `[floor, solid)`，被放行 |
| query 分布换域（商品咨询 → 投诉工单） | 问法更口语/更具体，命中分布整体位移 | 同一阈值对应的兜底率与业务预期脱节 |

「静默」是最危险的部分：代码能跑、测试能过，只有兜底率和幻觉率在悄悄偏移。

所以本项目的设计原则是：**阈值和"它在什么前提下成立"绑在一起**。运行时前提与 profile
不一致时不会被悄悄沿用，而是标 `stale` 并把原因写进 tracing / state。

### ⚠️ 尺度：两个尺度不能混用

`computeConfidence` 里的 `floor` / `solid` 是拿去和 **`topScore`（rerank 原始分数）** 比的。
而中间还有第二个量：**合成分数** `score = topScore × (1 − w + w × support)`，它是 topScore
的折扣后数值（量级更小，通常只有 topScore 的 6~8 折）。

标定必须在**和判决同一个尺度**上进行。早期实现把"合成分数尺度上选出的阈值"直接当 `floor` 用，
结果 `floor` 会跑到所有 `topScore` 之上——所有样本都走"低于下限"分支，中间地带与群像判据
**整段失效**，而单看混淆矩阵还不一定看得出来。现在：

- `floor` 由 `chooseFloor` 在 **topScore 尺度**上取（`src/confidence/calibration.ts`）；
- `solid` 由 `chooseSolid` 在同一尺度上取，且强制 `≥ floor`；
- `chooseThreshold` 出的阈值只作为**对照口径**（"如果链路只输出一个标量分数，工作点在哪"），
  以及 AUC 的排序量，**不再用来当 floor**。

有一条专门的测试守这个不变量（"★ 尺度回归"）：断言 `floor`/`solid` 落在观测到的
topScore 区间内、两根闸门不交叉，并用标定出的 policy 直接判两个构造样本自证语义。

## 2. 数据从哪来

标定输入是 JSONL，每行一条：

```json
{"id":"ticket-10231","chunkScores":[0.36,0.34,0.33,0.33,0.32],"shouldEscalate":true,
 "rerankerModel":"Qwen3-Reranker-8B","kbVersion":"kb-2026-03","domain":"商品咨询"}
```

| 字段 | 必填 | 含义 |
|------|------|------|
| `id` | ✅ | 稳定业务 id，能回溯到具体会话/工单，便于人工复核结论 |
| `chunkScores` | ✅ | 该次召回的 chunk 分数分布（**rerank 尺度**） |
| `shouldEscalate` | ✅ | 真实结论，口径见下 |
| `rerankerModel` / `kbVersion` / `domain` | ✅ | 标定前提；三个都参与分组，阈值不跨组借用 |
| `score` | ❌ | 当时链路实际算出的合成分数；缺省时按同一 policy 重算 |

### 为什么 `chunkScores` 是硬前提

闸门判决依赖 **top / min / 过线条数** 这些分布特征，不只依赖一个合成分数。而且
`floor`/`solid` 都作用在 rerank 尺度上。只落一个合成分数：

1. 标不出 `solid` 与覆盖度/区分度参数；
2. 连 `floor` 都会因为尺度错位而标错。

所以 schema **直接拒绝**没有 `chunkScores` 的记录（`parseJsonl` 会报错并指出行号）。
宁可让人去补数据，也不要产出一个尺度错位的阈值——那比没有阈值更危险。

落盘请用 `buildCalibrationRecord()`（`src/confidence/calibration-runner.ts`）：
它保证 `score` 与 `chunkScores` 出自同一个 policy，避免"分布"与"合成分数"对不上。

### 标签口径（`shouldEscalate` 怎么定）

正类 = "这条确实答不了 / 应该转人工"。可用以下几种信号，**优先级从高到低**：

1. **人工接管记录**：坐席接管后判定"知识库无答案"或补写了知识条目 → 强正样本。
2. **用户否定回流**：同一会话内继续追问同一问题、明确表示"答非所问"、或直接要求转人工 → 正样本。
3. **工单评价**：差评且原因是"没解决" → 正样本；要排除"答案对但态度差"的噪声。
4. **坐席编辑率**：交接包里的草稿被大幅改写（而非直接发送）→ 偏正样本，噪声较大，建议单独分桶观察。

负类 = "答得出来且答对了"。优先取「用户未再追问 + 无转人工 + 会话正常结束」。

> ⚠️ 不要用"模型自己觉得答得好"当标签，也不要用重算分数当特征——两者都会把偏差固化进阈值。

### 采集时机

线上就该落盘，而不是事后补录。每轮会话结束时写入一条含
`chunkScores / score / 是否转人工 / 是否有否定信号` 的记录。其中 `chunkScores` 可从 state 的
`contextChunks` 取（`state.confidenceDiagnostics` 已带预测级诊断，可直接一起落）。

### 没有实测数据时的替代路径：构造数据 + 决策带

实测数据缺失时，可以直接跑链路生成数据（`pnpm synthetic:data`）。但必须先把
**哪一部分是真的、哪一部分是编的**切开，否则会产出一份看起来很漂亮的假标定：

| 成分 | 真实性 | 说明 |
|------|--------|------|
| 分数 | **真的** | 真 embedding + 真 reranker + 真知识库，切块参数与生产一致 |
| 标签 | **构造的** | 由种子查询的 `stratum` 判定"知识库答不了"，不是人工接管记录 |
| 流行度 | **编的** | 正类占比由种子集构成决定，不等于线上真实求助分布 |

**为什么不直接用链路自己的输出当标签**：那是循环论证——拿 `lowConfidence` 当
`shouldEscalate`，等价于让闸门给自己出题，ROC 会漂亮得毫无意义。这正是"拍一个 0.35"
想避免的问题，换个体面的形式又犯一遍没有意义。

**构造数据能确定什么**：类内分布，以及由它决定的**决策带**——最难的负样本与最简单的正样本
之间那段可行阈值区间。`tpr` / `fpr` 都是类内比例，与两类占比无关，所以这段区间可以直接采信。

**构造数据不能确定什么**：线上负样本的**难度构成**。这里构造的负样本分两类，难度差一个量级：

- `out_of_scope`（话题完全不在库里）→ 分数贴近 0，是"容易的负样本"；
- `near_miss`（话题在库、具体答案不在）→ 分数落在中等区间，是群像高发区。

线上两者比例未知，而**决定阈值下界的恰恰是 `near_miss`**（见下面的实测）。所以按构造数据
得到的阈值应视为**下限附近**的估计：真实阈值大概率不低于它。

#### 守卫：构造数据不可能被当成本实测标定

`CalibrationRecord.provenance` 与 `ConfidenceProfile.provenance` 把这件事从"靠自觉"
变成"校验层强制"：

- 记录里**显式**写 `provenance: "constructed"`（生成器强制写入）；
- 一个组里只要混入一条 constructed，**整组降级**为 constructed——阈值是整组一起定出来的，
  无法把构造样本的贡献局部隔离，所以不允许混合组冒充实测；
- profile schema 的 `superRefine` 强制 `calibrated=true ⟹ provenance="measured"`，
  构造数据产出的 profile 必然是 `calibrated: false` + `provisional: true`；
- `describeResolution()` 把 `provisional` 打进 tracing 标记（`exact/provisional`），
  交接包的 `confidenceDiagnostics.provisional` 也会带上——否则两者在日志里长得一样。

#### 本轮实测结果（2026-09-15，真实链路）

30 条种子查询（可答 12 / 邻近缺参 8 / 域外 10），真 embedding + `BAAI/bge-reranker-v2-m3`
打 9 篇真实知识库：

| 地层 | topScore 范围 |
|------|--------------|
| 可答 | 0.4767 ~ 0.9891 |
| 邻近缺参 | 0.0044 ~ **0.3926** |
| 域外 | 0.0002 ~ 0.0419 |

- **决策带 = (0.3926, 0.4767]，带宽 0.0841，中点 0.4346。**
- **当前默认 `0.35` 落在这条带之外（下方）**：在这份分布上召回只有 15/18 = 83.3%，
  低于 90% 的目标。放行的三条是 C2(0.3764)、C5(0.3534)、C8(0.3926)——
  **全部来自 `near_miss`**，即"话题在库里、具体答案不在"。也就是说 `0.35` 不是保守，
  而是**偏低**；它漏掉的恰好是最危险的那类问题。
- 撑住上界的不是"话题完全不在库"那批，而是 `near_miss`——与 §4 的群像分析一致。
- **这条带是脆的**：拿掉决定它的单条样本后带宽变成 0.1776 / 0.1003，变化比带宽本身还大，
  说明它由少数样本撑起。所以正确结论不是"就用中点 0.4346"，而是
  "补更多落在 0.30~0.50 区间的标注"。

> 注意别把这里的数值当成可直接采用的阈值：它来自 30 条构造样本，`fit/holdout` 切分后
> 每组只有 21/9 条，连 `floor` 的标定门槛（≥20 支撑样本）都过不了，CLI 会如实报
> "floor 未标定，沿用默认值"。这些数字的价值是**指出 0.35 偏低以及为什么**，
> 不是提供一个替代常数。

#### 顺带发现的一条新漂移轴：切块形状

同一个 chunk，作为孤立单句送进 reranker 时相关文档只有 `0.1571`；按生产的
"文首标题块 + 章节正文" 组织后同一内容能到 `0.97`。也就是说 **rerank 分数尺度不只取决于
模型，还取决于 chunk 的组织方式**。现有 profile key 里有 `kbVersion`，但如果只重新切块、
不 bump 版本号，阈值就会在新的分数尺度上静默失效。**重新切块必须 bump `kbVersion`。**

#### ⚠️ 上表那条"决策带"是**易负样本**下的结果——模拟真实措辞之后它就塌了

上面那个 `(0.3926, 0.4767]` 的带，是用**手写种子查询**算出来的，结论看起来是
"0.35 只是略低"。这个结论**站不住**，因为手写查询的措辞偏书面、与文档用词高度重合，
负样本偏容易。用真实措辞重做之后（见下），可答问题的分数跨度是 **0.032 ~ 0.995**。

### 能模拟真实用户来测吗

能，但必须把"模拟输入"和"模拟标签"分开——**前者可行且有价值，后者会系统性地骗自己**。

#### 模拟用户为什么不能当标签

不是"模型不够像人"，而是结构性缺陷：模拟用户能看到的只有**答案文本**，
而群像式幻觉的定义特征恰恰是"答案读起来很顺、很确定"。所以"看起来满意"与
"其实被编造骗了"在模拟用户眼里是同一种东西。

更糟的是这个偏差**有方向**：它会系统性地说"解决了"，于是拿它当标签会**调低**阈值、
让更多编造内容通过。所以它比"没有标签"更差。

#### "那你自己当真实用户去用系统不就行了"——解决不了

这个提议听起来绕开了"模拟"，但没有绕开要害：**决定信号质量的是信息，不是身份。**

**"真实用户"与"知道答案"是互斥的。** 真实用户按定义不知道答案，所以他给出的"满意"
只包含"看起来像答了"这一层信息，与"答案对不对"无关；而一旦我拿着知识库去核对，
我就不再是用户，而是**有标准答案的评测者**——那时我根本不需要"去用系统"，
只需要对照知识库，而那正是消融法在做的事，且更可靠（构造事实 > 我的判断）。
换句话说：能当用户时没有真值，有真值时已经不是用户。

**但有一类信号确实只有"用起来"才拿得到，且不需要真值**：**答非所问**。
"我问怎么申请价保，它回了一堆价保规则"——这个从问答对本身就能看出来，
不需要知道正确答案。这恰好是实测里最常见的那一类（消融后模型拿邻章内容答了另一个问题）。
代价是它只能筛掉**明显的偏离**，而漏掉"看起来很对但其实错"的那一类——
也就是闸门最该拦的那一类。

#### "那开一个子智能体当真实用户呢"——它确实不知道答案，所以这条得实测

这条质疑是对的：**子智能体确实是一个真实用户**（它没有知识库）。所以问题不在身份，
而在**这个标签测的是什么量**。这件事被实测了，而不是论证
（`src/confidence/user-agent.ts`，`pnpm probe:user-sim --user-agent`；20 个知识库章节
× 2 条件 × 2 人格 = 77 条样本，真 LLM 作答，用户子智能体只看得到"问题 + 回答"）。

| 人格 | 答不了却说「答上了」 | 答得了却说「没答上」 | 与真值一致率 |
|------|-------------------|-------------------|------------|
| 普通客户 | **7/19 = 36.8%** | 0/20 = 0% | 82.0% |
| 挑剔客户 | 3/18 = 16.7% | 3/20 = 15.0% | 84.2% |

- **普通客户（= 真实用户的样子）在 36.8% 的"知识库给不出答案"的问题上说"答上了"。**
  这就是把用户判断当标签时的漏标率，而它漏掉的正是闸门存在的理由。
  用户给的理由很直白：「给出了 15 天和 30 天等具体时间节点，整体看起来是在直接回答」——
  他看到的是一段笃定、具体、**且确实来自知识库**的回答，只是答的不是被问的那件事。
- **挑剔人格把漏标降到 16.7%，但这不是"用户变聪明了"**：它之所以做得到，
  是因为被明确要求核对「有没有**正面回答你问的那件事**」——**那时它已经是个评委，不是用户**；
  代价是反过来把 15% 的**答得了**判成没答上。而且两者的与真值一致率几乎一样（82% vs 84%）。
- **最决定性的一条：照提案的做法（拿 `!用户说答上了` 当 `shouldEscalate`）去选阈值，
  两种人格都选不出来**——可行区间宽度 −0.9045 / −0.8704，两类不可分。
  也就是说这套标签连一个阈值都导不出来。原因在样本里直接可见：
  用户说"答上了"的那条 topScore 是 0.0055，而它说"没答上"的那条是 0.91，
  **用户判断与分数排序不同向**——这不是"一个更差的标签"，而是一个和特征不同向的标签。
  对照：现役基线 `floor=0.35` 在同一批样本上是误伤 20.0%、漏放 30.0%。

**所以结论**：用户子智能体的正确用途是**找 bug**（它确实暴露了大量"答非所问"，那是有价值的）
和**生成输入分布**，而不是当标签。要拿它当标签，就得给它注入"核对有没有正面回答问题"
这类评委指令——而那正是上一节已经实测为更差的那个判据。
**把用户变好的过程，就是把它变成评委的过程；而评委这条路已经测过了。**

#### 模拟输入能做什么

由知识库章节**自指令合成真实措辞的问题**（`questionSynthesisPrompt`），只生成输入、
不生成标签。这一步的价值是手写种子集根本给不出的：**真实措辞**。

实测（43 个章节各合成一题，`pnpm probe:user-sim`）：

| 指标 | 手写种子（措辞书面） | 合成问题（措辞真实） |
|------|---------------------|---------------------|
| 可答问题 topScore 下限 | 0.4767 | **0.0323** |
| 可答问题被 `floor=0.35` 误伤的比例 | **0/12 = 0%** | **10/40 = 25.0%** |

那 10 条误伤样本逐条核对过，全部是**答案确实在库里、且承载它的章节在全库检索时排前三**
的问题（例："你们那个会员都分几档啊，每一档分别有啥特别的福利？" 对应的正是那张会员等级表，
分数 0.0396）。判它们低置信是纯粹的误伤，会变成没必要的兜底话术或转人工。

**所以 `floor` 实际上主要在衡量"用户问得像不像文档"，而不是"知识库答不答得了"。**
这一点只有模拟真实措辞才测得出来——这也是"能不能模拟真实用户"这个问题的正面答案：
能，而且它立刻找出了问题。

#### 标签从哪来：答案消融（ablation）

同一个问题跑两遍，一遍保留承载答案的那一节、一遍把它从候选池里拿掉：

- 保留 → 答得了（负类）
- 消融 → 承载答案的那一节不可用（正类）

标签来自**代码执行的事实**，不来自任何模型判断。配套两个确定性检查：

1. **`checkSynthesis`**：全库检索时源章节必须排前三，否则问题与该节主题不符、消融后无法归因。
2. **`measureAblationResidue`**：被消融章节有多少比例的句子在**别处照样能找到出处**
   （字符 6-gram 匹配）。残留过高说明知识库在别处重复写了同样的内容，
   消融没有真的移除答案，这条不能当负样本。**这一步同样不调模型**——
   用模型判断"答案还在不在"，等于把模型判断重新引回标签。

顺带产出一个知识库体检结论：这份 9 篇知识库的**逐字重复很低（1/43 = 2%）**，
所以消融本身是有效的。

#### 实测结论：单阈值撑不住（这是对第一问的实质回答）

40 条有效消融样本、真 LLM 作答（用生产 `GENERATE_PROMPT`）：

- **可答问题 topScore 跨度 0.0323 ~ 0.9945**，25% 低于 `0.35`。
- **决策带不可分**（带宽 −0.8790）：一条**模型自认找不到依据**的问题拿到 `0.9113`，
  而一条**答案确实在库里**的问题只拿到 `0.0323`。
- 干净子集复核（正类只保留模型自认找不到依据的 24 条，负类仍 40 条）**仍然不可分**。
  两侧标签都经过核实，所以这不是标注噪声造成的。
- 在被消融的上下文下，**40% 的回答没有承认"知识库里没有依据"**，而是给出了一段笃定回答
  （其中 2.5% 编造了上下文里根本没有的具体数字）。
  注意生产 prompt 里**已经**写明"上下文未覆盖的内容…不要编造"，所以这是
  **在明确禁止的前提下仍然发生**的比例。

**结论修正**：第一问的答案不是"0.35 偏低"，而是**"用 topScore 单阈值来判断
'知识库答不答得了'这个做法本身形状就不对"**——它主要响应的是措辞相似度。
继续调这个数只会在两个方向的错误之间来回搬。

**而且"换一个更好的判据"也试过了，实测更差**（属性覆盖判据：误伤 23.8% 持平、漏放从 26.2% 涨到 50.0%）。
根因是词法判据分不清"同一主体的哪个属性"。详见 §8 对应条目——**这是一条已经被测量过的死路**，
不是"还没试"。所以下一步不该再往"判据"上使劲，而应绕开它（引文强制、接受低置信为常态、从检索侧治）。

> `answeredFromRemaining` 这个数字（答案能否从剩余章节拼出来）**不是**模型判断的标签，
> 只是一个提示：消融拿掉的是"承载答案的那一节"，不保证整库都答不了。所以正类标签有噪声，
> 上面才额外做了干净子集复核。

#### 一个被测试抓到的实现 bug，值得单记

"承认不知道"的识别是一张**措辞表**，第一版**漏了 `GENERATE_PROMPT` 里明确要求模型说的那句
"这个问题我需要进一步确认"**——于是最常见的那句承认话反而识别不出来，
`admitsIgnorance` 从 60% 被压到 12.5%，连带把"没承认"的比例从 40% 抬到 87.5%。
**话术表必须对着生产 prompt 的实际措辞写，不能凭印象列。**

## 3. 标定流程

```bash
# 单次标定
pnpm calibrate --input data/handoff-2026Q1.jsonl --out config/confidence

# 收紧业务约束：召回 ≥ 95%，误伤 ≤ 20%
pnpm calibrate --input data/handoff.jsonl --out config/confidence --target-recall 0.95 --max-fpr 0.2

# 与上一版对比分布漂移（PSI）
pnpm calibrate --input data/handoff-2026Q2.jsonl --out config/confidence \
  --baseline data/handoff-2026Q1.jsonl
```

### 五个阶段

| 阶段 | 做什么 | 做法 |
|------|--------|------|
| 0 | 切分 | `splitCases`：按 `hash(id)` 排序后取前 N 条进**留出集**（默认 30%）。比例精确、结果可复现、与输入顺序无关。**所有拟合只用标定集，留出集全程不参与选择** |
| 1 | 定 `floor` | `chooseFloor`：取**最大的**分数 s，使得 `topScore < s` 的样本里"其实答得出来"的比例 ≤ `--floor-tolerance`（默认 5%）。语义：低于这条线，基本可以认定库里没有 |
| 2 | 定 `solid` | `chooseSolid`：取**最小的**分数 s（且 `s ≥ floor`），使得 `topScore ≥ s` 的样本里"仍需转人工"的比例 ≤ `--solid-tolerance`（默认 5%）。语义：过了这条线，单条命中就可信 |
| 3 | 联合优化其余参数 | 坐标下降：把真实闸门函数（`computeConfidence`）当黑盒，在**派生网格**上搜索 6 个参数，判据是业务约束下的（召回，误伤，精度）字典序 |
| 4 | 样本外验证 | 用留出集评估最终 policy，算泛化差距并判过拟合嫌疑（`judgeGeneralization`） |
| 5 | 敏感性报告 | 把每个参数在候选值上的表现摊开，判断落在**平台期**还是**刀尖**上（`sensitivityReport`） |

两个参数标不出来时（样本量不足、或某个方向根本达不到容忍度）**不会**拿外推值冒充标定产物，
而是保留保守默认值并在 `notes` 里写清原因。

**不变量**：`floor ≤ solid`。相等表示"中间地带塌缩"——两支样本的 topScore 完全分开了，
闸门退化为单阈值判决。这是正常结果，但会被显式记进 `notes`，因为它意味着
覆盖度/区分度判据没有被用到。

坐标下降是**贪心**的，不保证全局最优。选它而不选全网格搜索，是因为 6 个参数的全组合会把
评估次数乘到不可控，而这里真正重要的是**可解释**——报告能说清每个参数为什么落在那个值上。

### 候选网格是从观测分布派生的，不是拍的上下界

「网格上下界由人工给」之所以是个缺口，理由不是洁癖：如果候选值没覆盖到真正可用区，
坐标下降会停在一个"看起来达标"的错位置上，而报告里看不出这件事。
所以能派生的都派生（`derivePolicyGrid`），并在报告里**说明每个参数的候选值为什么是那些**：

| 参数 | 候选来源 |
|------|----------|
| `floor` / `solid` | 观测 topScore 的分位点（阈值只有落在实际取值上才改变判决） |
| `minRange` | 观测落差 `top-min` 的分位点，上界 = 最大落差（超过它区分度永远达不到 1） |
| `minSupportShare` | 观测「过线条数占比」的分位点 |
| `flockDiscriminationMax` | 观测区分度的分位点（按初始 `minRange` 归一，以打断循环依赖） |
| `coverageWeight` | **无法派生**。它是合成分数的混合权重，不锚在任何观测特征上，只能给固定覆盖面——报告里会显式标出这一点，不假装它是数据推出来的 |

`initial` 的当前值一律纳入候选，保证搜索**不会比初值更差**。
`--grid-resolution` 控制分位点数量。

### 样本外验证：这才是"网格能不能加细"的前提

把网格加细本身毫无技术难度；难的是**加细之后你还能不能相信选出来的值**。
当相邻候选之间的指标差异小于抽样噪声时，坐标下降挑的是噪声。没有样本外验证，
就无法区分"真的更好"和"在这份标注集上恰好更好"。

所以先解决"能不能信"，再谈"能不能更细"：

- 拟合全程只用标定集，留出集不参与任何选择；
- 最终 policy 在留出集上复算，得到**无偏参照**；
- `judgeGeneralization` 判过拟合，判据的核心是**用训练集自身的置信区间宽度当噪声底线**：
  差距落在这个宽度之内说明不了任何事，只有超出才算过拟合证据。这条规则的好处是
  **随样本量自动收紧**——样本越多，能容忍的差距越小。

判为过拟合嫌疑时会打 ⚠️ 并让 CLI 非零退出，`profile.generalization.overfitSuspect` 也会置真。
留出集小于 20 条时**不给结论**，只提示"上面的成绩只反映标定集"——样本太少时差距全在噪声里，
硬给一个"通过/不通过"反而是编造。

### 敏感性：这个选择落在平台期还是刀尖上

`sensitivityReport` 把每个参数在候选值上的表现摊开，`summarizeSensitivity` 压成结论：

- **稳**：多数其他候选值同样可行 → 处在平台期，选哪个都行；
- **脆**：只有当前值可行、隔壁就崩 → 这份标定是脆的，换一批样本很可能翻（报告里会点名）。

### 工作点的判据

坐标下降的 `feasible` = **`fpr ≤ maxFpr` 且 `tpr ≥ targetRecall`**，两个约束缺一不可：

- 只给召回下限 → 退化成"全部转人工"（阈值拉满时 TPR 恒为 1，天然达标）；
- 只给误伤上限 → 退化成"一律不转"。

代价不对称是选择依据：漏掉一个"知识库没有"的问题，用户会读到一段语气笃定的编造内容；
误判一个能答的问题为低置信，只是多一次兜底话术或转人工。所以判据先保召回、再压误伤。

> `--mode youden|precision_floor` 仍可用，但只影响**对照口径**那行输出，不再决定 profile。

## 4. 群像式幻觉（flock hallucination）

**定义**：query 在知识库里没有答案，但召回出来的一簇 chunk 分数都"勉强够用"且互相没有区分度。
合成出的答案读起来很顺，每条引用单独看都"还算相关"，因此比单纯的检索失败更难发现。

**判据**（`src/nodes/confidence.ts`）：

```
flockHallucination =
  chunks.length >= flockMinChunks       // 至少 3 条，"分布形状"才有意义
  && floor <= topScore < solid          // 没有一条达到"实心线"
  && discrimination <= flockDiscriminationMax
```

三条配套判据一起生效，缺任一条都会漏：

1. **coverage 用绝对口径**（分数 ≥ floor 的占比）。相对口径（"接近最高分"）会把
   "大家都差不多差"算成 100% 覆盖。
2. **区分度下限**。整簇都略高于 floor 但落差极小时，靠覆盖度挡不住，必须靠区分度。
3. **旁证至少 2 条**。占比在候选集很小时会骗人（2 条里 1 条过线就是 50%）。

`flockHallucination` 会写入 state、tracing、`degradations` 与**交接包**，并且现在有两条统计口径：

- 标定报告里的 `群像触发=X/n`（标注集上的触发率）；
- 评测指标 `flockHallucinationCount`（回放集上的命中数）。

交接包里带的是 `confidenceDiagnostics`（阈值出处、标定状态、coverage、区分度、群像标记）——
坐席需要的不是"置信度 0.28"，而是"为什么低"：知识库里没有，还是召回的是一簇勉强相关的 chunk。
后者答案读起来很顺，最容易被当成可信内容直接发出去。

### ⚠️ 闸门不移除编造内容——移除它的是输出侧 grounding

一个容易误解的点：低置信只做两件事——**套不确定表述** + 两轮后转人工。它**不会**把编造的具体
内容从答案里去掉。真正把编造拦在用户之外的是 `guardrails/output.ts` 的确定性检查
（`Reviewer.review()` 第一步就跑它，失败即短路）：

- 金额（`¥120.00` / `120 元`）与 8 位以上账号/订单号 → 必须能在 citations 里找到；
- **承诺性百分比**（`99.99%` / `百分之99.9`）→ 同样必须能找到。

> 这条百分比规则是 dogfooding 补上的：原先只覆盖金额与长数字，于是「我们承诺 99.99% 的可用性」
> 这种"看起来很具体、其实无出处"的承诺能一路发出去——而它恰恰是群像式幻觉最典型的产物。
> 比对用的是**数字核心**（`99.99`）而不是整串（`99.99%`），因为引用里常写成
> "可用性 99.99" / "99.99 per cent"，整串匹配会造成格式性误杀（本文件已因类似问题踩过一次坑）。
>
> 已知不覆盖：`3 个 9` 这类写法需要归一化（"3 个 9"的承诺强度不是数字 3），未纳入；
> 裸的"承诺"字样属语气问题，交给 overpromise 规则与模型终审。

对应评测：`general-003`（群像 + 编造 99.99% → 被拦、转人工、**编造数字不出现在用户话术**，
但草稿完整进交接包供人工编辑）与 `general-004`（群像 + 不编造 → 低置信话术正常到用户）。
两个场景分开测，避免"闸门触发了"被误读成"编造被移除了"。

## 5. 参数现状（诚实版）

| 参数 | 值来源 | 状态 |
|------|--------|------|
| `floor` | `chooseFloor`（topScore 尺度） | ✅ 数据驱动 |
| `solid` | `chooseSolid`（topScore 尺度，受 `floor` 下界约束） | ✅ 数据驱动 |
| `minRange` / `minSupportShare` / `flockDiscriminationMax` | 坐标下降，候选值取观测分布分位点 | ✅ 数据驱动 |
| `coverageWeight` | 坐标下降，候选为固定覆盖面 | ⚠️ **仍属设计选择**：它是合成分数的混合权重，不锚在观测特征上，派生不出来（报告里已显式标注） |
| `flockMinChunks` | 固定 3 | ⚠️ 统计常识（分布形状需 ≥3 点），未标定 |

也就是说：**"拍脑袋"只剩下两处**，且都被显式标注：

1. `coverageWeight` 的候选覆盖面——它是混合权重，没有数据锚点；
2. `flockMinChunks` 的 3——属于统计常识而非可从本数据推出的量。

网格**加细**本身随时可做（`--grid-resolution`），但能不能相信更细的结果，取决于留出集大小：
泛化差距与敏感性报告会直接告诉你当前分辨率下这个选择是否稳健。**所以"网格够不够细"不再是
一个未知量，而是一个被测量的量**——样本量上来后调大 `--grid-resolution`，若敏感性仍显示"稳"
且泛化差距仍在噪声内，就可以采信。

## 6. 端到端验收

闸门此前**不在任何端到端验收范围内**：评测回放给所有 chunk 恒定 0.9 分，于是
"单条强命中"恒成立、闸门从不触发。现在：

- `script.chunkScores` 可为每个 chunk 指定分数（长度必须与 `retrievedChunks` 一致，否则 schema 报错）；
- `expected.lowConfidence` 可声明期望的判决，参与 pass/fail；
- `general-003` 就是一条群像场景（`chunkScores: [0.36,0.32,0.31,0.31,0.3]`），断言
  「闸门判低置信 + 用户话术里真的带上了不确定表述」；
- 指标新增 `lowConfidenceRate` 与 `flockHallucinationCount`。

**mutation 验证**：把 coverage 改回相对口径，这条评测用例会红（`supportCount` 5 ≠ 1）；
在此之前，任何闸门回归都不会被评测发现。

## 7. 漂移监控

三个信号，任何一个异常都应触发重标：

1. **`confidenceProfileStale` span 属性为 true**：运行时前提与 profile 不一致。
   **这是最先该看的一条**——它通常意味着上线时漏了重标，而不是模型变差了。
2. **PSI（群体稳定性指标）**：`--baseline` 与本次数据比较 **topScore 分布**
   （闸门真正看的那个量）。
   - `PSI < 0.1`：稳定，沿用；
   - `0.1 ≤ PSI ≤ 0.25`：有漂移，人工复核；
   - `PSI > 0.25`：显著漂移，**不可直接沿用**，重新标定。
3. **线上兜底率 / 转人工率**：与标定时的预期（`1 - tpr`、`fpr`）对比。
   偏差超过 Wilson 置信区间上界，说明前提变了。

## 8. 已知局限

- **闸门只管"放不放行"，不管"内容删不删"**：低置信不改写答案文本，编造内容由输出侧
  grounding 拦截（见 §4）。而 grounding 目前只覆盖金额 / 长数字 / 承诺性百分比，
  **不覆盖** `3 个 9` 这类需归一化的写法，也不覆盖裸的"承诺"字样。
- **仍未跑过真实历史人工接管数据**。项目当前没有生产数据回流，所以
  **阈值本身仍然没有被真正标定过**。缺的不是工具链，是标注数据。
  - 已经能做到的：用真链路 + 构造标签产出 **provisional 先验**，
    并给出决策带，指出默认 `0.35` 偏低（见 §2「没有实测数据时的替代路径」）。
  - 仍然做不到的：把构造数据变成实测标定。流行度与真实负样本难度分布都是构造的，
    这不是算法能补的，统计手段也自证不了。
  - 仓库里的 `tmp/synthetic-calibration/*.jsonl` 与 `tmp/demo-calibration*.jsonl`
    **都不是**真实阈值依据。
- **构造数据的种子集只有 30 条**，且 `near_miss` 只占 8 条——而它恰恰是决定阈值下界的那个地层。
  决策带的宽度由极少数样本撑起（见 §2 实测），所以那几个数只能当方向性证据，不能当选值依据。
  **而且已经证明它偏乐观**：换成模拟真实措辞之后，可答问题的分数下限从 0.4767 掉到 0.0323，
  那条"决策带"直接塌掉（见 §2「能模拟真实用户来测吗」）。
- **`floor`（topScore 单阈值）作为判据的形状本身有问题**：实测它主要响应措辞相似度，
  而不是"知识库答不答得了"。同一条知识，用户问得像文档时 0.99、问得像口语时 0.03。
  这意味着当前闸门**同时**存在大量误伤（可答问题被判低置信）与漏放（答不了的问题没被判低置信）。
- **已经试过"换个更好的判据"，实测更差——这条死路已被测量并记录**
  （`src/confidence/coverage.ts`，判据评测台见 `pnpm probe:user-sim --judge-compare`）。
  实现的候选判据是"用户问的那个**属性**（时长/金额/数量/条件/能否…）在上下文里到底有没有给出取值"，
  判据 = 存在一句话同时含该属性的**取值模式**与问题**主体词**。在同一批 84 条同源样本上：

  | 判据 | 误伤 | 漏放 |
  |------|------|------|
  | `topScore < 0.35`（基线） | 23.8% | 26.2% |
  | 属性覆盖 | **23.8%** | **50.0%** |

  **误伤一点没改善，漏放翻了一倍。** 根因是词共现这个抽象太粗：会被**同一主体的另一个属性**满足。
  实测那条例外——问"退差价**多久能到账**"，上下文里有「一般商品：签收后 **15 天内**降价可**申请**价保。」，
  主体词与属性都在同一句，但那是**申请时限**，不是**到账时效**。
  要区分"同一主体的哪个属性"必须理解语义，而用模型做语义判断会带回同一个病根。
  另一半原因：26.2% 的样本它**不表态**（问法没有可靠词法特征），弃权后回落基线，该修的误伤原样留下。
- **所以正确的下一步不是"再找一个判据"，而是绕开判据**（三条候选路线，都还没做）：
  ① 答案必须引用"支撑它的那一句"，缺引用即 fail-closed；
  ② 承认"低置信 → 兜底/转人工"是常态，按实测比例（约 1/4）做成本预算；
  ③ 从检索侧治——提高问题所问**参数**的可召回性，而不是事后判它有没有被召回。
- **模拟用户不能当标签**（见 §2）：它对"流畅的编造"免疫，且偏差有方向（系统性地说"解决了"），
  拿它当标签会调低阈值、放进更多编造内容。它的正确用途是生成输入分布。
- **"让子智能体当真实用户"也不行，而且已经实测**（见 §2）：普通客户在 36.8% 的
  "知识库给不出答案"的问题上说"答上了"；照用户标签选阈值，两种人格都**选不出阈值**
  （用户判断与分数排序不同向）。把用户变好的唯一办法是给它注入评委指令，
  而那正是本轮已实测更差的那条路。用户子智能体的正确用途是**找 bug** 与生成输入。
- **环境依赖会让链路随时不可跑，这不是代码问题**：本轮 SiliconFlow 账号余额耗尽，
  **Embedding 与 Rerank 同时返回 402**（LLM 侧仍正常）；同时 Qdrant 这次是**起着的**
  （上一轮是 down）。所以"链路能不能跑"每次都要实测，不能凭上一次的印象——
  这类变化会让人误以为自己写错了代码。
- **消融样本的正类标签仍有噪声**：消融拿掉的是"承载答案的那一节"，相邻章节可能给出部分答案。
  残留度检查只能拦**逐字重复**，拦不住"信息可由邻章拼出来"。所以消融实验的正类需要
  干净子集复核（只保留模型自认找不到依据的那批）才能下结论。
- **`coverageWeight` 的候选覆盖面仍是设计选择**（见 §5），`flockMinChunks` 固定为 3。
- **`shouldEscalate` 标签口径需与业务方确认**，尤其"坐席编辑率"这路信号的噪声水平。
- **多域 profile 的运行时切换未实现**：profile 已支持按 `domain` 分组，但同一部署内
  按会话/租户路由到不同 profile 还没做（当前一次 `buildGraph` 只解析一份）。
- `flockHallucinationCount` 目前只在回放集与标定集上有数，线上触发率仍需要落盘数据才能统计。
- **泛化验证只能证明"在这份标注集上不过拟合"**，不能替代真实流量验证。留出集与标定集来自
  同一批数据、同一采集方式，若有系统性采样偏差（例如只标了容易判断的 case），
  两边都会被同样的偏差带偏。这一点无法靠统计手段自证，必须靠采集流程设计。
  构造数据把这个局限放大了：种子集是**一个人写的**，偏差面更大。
- **重新切块必须 bump `kbVersion`**：rerank 分数尺度同时取决于模型与 chunk 组织方式，
  只改切块不改版本号会让阈值静默失效（见 §2 实测）。
